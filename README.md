# onvif-bulk-codec

Массовый перевод IP-камер видеонаблюдения с H.264 на H.265. Разрешение, битрейт, FPS и GOP при этом сохраняются, а каждая камера после смены проверяется. При том же качестве H.265 занимает в архиве NVR заметно меньше места и меньше нагружает сеть.

## Почему два способа

Сначала я написал смену кодека через ONVIF (`SetVideoEncoderConfiguration`). Камеры TpseeCAM **принимали запрос, отвечали «OK», но ничего не меняли**. Их собственный веб-API шифруется (ECDH + WASM), поэтому вызвать его напрямую не получилось. В итоге смена кодека идёт через настоящий веб-интерфейс камеры в headless Chromium (Playwright), а результат проверяется независимо, через ONVIF и `ffprobe` RTSP-потока.

| Файл | Что делает |
| --- | --- |
| `onvif_lib.py` | Минимальный ONVIF-клиент на чистом Python: SOAP, WS-Security digest, Media2. Подстраивается под часы камеры и перебирает пароли |
| `inventory.py` | Только чтение: модель, прошивка, текущие настройки энкодеров и есть ли H.265. Сохраняет **бэкап** конфигурации каждой камеры в `backup/<ip>.xml`. Работает в 16 потоков |
| `set_codec.py` | Смена кодека через ONVIF (для прошивок, где это работает) с проверкой после записи |
| `web_codec.mjs` | Смена через веб-интерфейс: `--dry-run`, 4 камеры параллельно. Если другие поля формы изменились, запись отменяется. Проверка после перезапуска камеры, скриншот при ошибке |
| `probe_rtsp.py` | Независимая проверка: какой кодек реально идёт в main/sub RTSP-потоке (`ffprobe`) |

## Порядок работы

```bash
cp cams.txt.example cams.txt                 # IP камер
printf 'pass1\npass2\n' > ~/.config/onvif-pass && chmod 600 ~/.config/onvif-pass
python3 inventory.py                          # бэкап + что поддерживает H.265
npm install
node web_codec.mjs --dry-run $(cat cams.txt)  # что изменится
node web_codec.mjs $(cat cams.txt) | tee rollout.jsonl
python3 probe_rtsp.py $(cat cams.txt)         # проверить фактический кодек
```

## Подводные камни

- Прошивка IPNC падает на `GetVideoEncoderConfigurations` без токена, поэтому конфигурации запрашиваются по одной, с токенами из профилей.
- Камера может указать в `XAddr` чужой IP, поэтому из адреса берётся только путь, а IP подставляется тот, по которому мы к ней обращаемся.
- Если часы камеры расходятся с нашими, digest отклоняется. Поэтому клиент берёт время камеры через `GetSystemDateAndTime` и отстаёт от него на 5 секунд.
- WASM-модуль логина камера отдаёт с неправильным MIME-типом, и он грузится медленно. Если нажать «Войти» раньше, ничего не произойдёт, поэтому скрипт ждёт `Module.calledRun`.
- Пароль никогда не попадает в вывод: в ошибках `ffprobe` он заменяется на `***`.
